# Agents with Memory

By default, each request is independent — the agent doesn't remember previous messages. Memory fixes that.

## How it works

Every request that comes through the web interface carries a `context_id` — one per session, generated by the backend. The framework hands it to your task if the task asks for it in its signature. Anything you store in the **session context** under that `context_id` is there again on the next request of the same session.

So memory is three explicit moves, all in your task:

1. Read what the session already holds
2. Put it in the prompt
3. Write the new turn back

Nothing is remembered behind your back. You decide what the model sees.

```{note}
`invoke()` does not keep a conversation between calls on its own. Each call starts fresh — pass the history in the prompt, as below.
```

## Add memory to your agent

The step receives the history as plain text and puts it in front of the model:

```python
from app import agent
from config import config
from abi_core.agent.llm_provider import invoke


@agent.step(name="chat_with_memory")
async def chat_with_memory(text, history=None):
    """Respond, taking the earlier turns of this session into account."""
    prompt = f"Conversation so far:\n{history}\n\nUser: {text}" if history else text
    result = await invoke(config.LLM_CONFIG, prompt)
    return {"response": result}
```

The task reads the session, calls the step, and records the new turn:

```python
from app import agent
from abi_core.agent.agent_response import AgentResponse
from abi_core.common.utils import format_conversation_summary


@agent.task(name="chat", task_id="task-chat")
async def chat(query, context_id=None):
    # The framework passes context_id in for you — one per session.
    session = await agent.get_session_context(context_id)
    turns = session.get("conversation_summary") or []

    result = await agent.execute_step(
        "chat_with_memory", text=query, history=format_conversation_summary(turns)
    )

    # Keep the last 10 turns.
    turns = (turns + [{"user": query, "assistant": result["response"]}])[-10:]
    await agent.update_session_context(context_id, {"conversation_summary": turns})

    yield AgentResponse.result(result)
```

`format_conversation_summary` turns the list into `User: ...` / `Assistant: ...` lines, or `None` when the session is new.

## Test it

Memory belongs to a session, so start one and send its token with every message:

```bash
# 1. Start a session
TOKEN=$(curl -s -X POST http://localhost:8002/session/start | jq -r .session_token)

# 2. First message
curl -N -X POST http://localhost:8002/stream \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"query": "My name is Carlos"}'

# 3. Second message — same token, same session
curl -N -X POST http://localhost:8002/stream \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"query": "What is my name?"}'
# → "Your name is Carlos"
```

Sending a `context_id` in the request body does nothing — the backend always uses the one tied to the token, so nobody can read another user's conversation by guessing an id.

## How context_id works

- Same token = same `context_id` = same conversation
- No token = a fresh anonymous session on every request (no memory)
- New token = fresh conversation

## Where the memory lives

By default the session context lives in the agent's process (`SESSION_BACKEND=memory`). If the container restarts, it's gone, and two replicas don't share it. Set `SESSION_BACKEND=redis` and the same code keeps working across restarts and replicas — see [Sessions & Multi-turn](07-sessions-multi-turn.md).

## Persistent memory with the Agent Memory Server (AMS)

The two kinds of memory are different:

- **Session memory** (this page) — the recent turns of one conversation, kept in the session context. Simple, scoped to a session.
- **Built-in memory API** — a system-wide store any agent can opt into, backed by the Agent Memory Server (AMS) and persisted in Redis. It captures things worth keeping deliberately (a pending clarification, results of past tasks, a user preference), survives restarts, and any agent — not just a swarm's — can query it.

`abi-core add service agent-memory` provisions it with two services (`<project>-redis-stack` + `<project>-agent-memory`) and works for a single agent created with `abi-core add agent` exactly as well as for a multi-agent setup — it is **not** swarm-specific. The full write/read API, the `MEMORY_TOOLS` for LLM-driven recall, and the AMS environment variables are covered on the next page — this section is just the pointer.
